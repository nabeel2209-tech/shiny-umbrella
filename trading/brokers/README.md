# Broker adapters

The engine talks only to the Protocols in `base.py`. Adapters translate to a broker's
API and enforce constraint 6 (tz-aware IST timestamps, canonical symbols) at the boundary.

## Base URL, headers, auth

- REST base: `https://api.dhan.co/v2/`. JSON in and out. GET/DELETE params as query params.
- Headers on every request: `access-token: <JWT>`, `Content-Type: application/json`.
  Data/quote endpoints also want `client-id: <dhanClientId>`; we send it everywhere.
- Access token: generated on web.dhan.co → My Profile → *Access DhanHQ APIs*, or via
  `POST https://auth.dhan.co/app/generateAccessToken?dhanClientId=&pin=&totp=` when TOTP is
  enabled (v2.5). **Valid 24 hours** from generation (v2.4, SEBI rule). Response carries
  `expiryTime` (ISO 8601). The token is a JWT, so we read its `exp` claim locally to know when
  it dies.
- Renewal: `POST /v2/RenewToken` with headers `access-token` and `dhanClientId`. Only renews an
  *active* token; an expired one must be regenerated by hand. `TODO(dhan)`: the response body
  shape is not documented — the adapter accepts an `accessToken` key if present, otherwise
  keeps the current token and logs.
- An "API key" flow with 1-year validity exists (v2.4). Not implemented.
- **Static IP whitelisting is mandatory for all order APIs** (place/modify/cancel). Not needed
  for data. Set it in the Dhan web portal; it cannot be changed for 7 days afterwards.
- Data APIs (historical, live feed, quotes) need the paid *Data API* subscription on the
  account (error `DH-902` / `806` otherwise).

## Rate limits (from the intro page)

| Category | /second | /minute | /hour | /day |
|---|---|---|---|---|
| Order APIs | 10 | 250 | 1000 | 7000 |
| Data APIs (historical) | 5 | – | – | 100 000 |
| Quote APIs (`/marketfeed/*`) | 1 | – | – | – |
| Non-trading APIs (order book, positions, funds…) | 20 | – | – | – |

Max 25 modifications per order. Exceeding limits returns `DH-904` (trading) or `805` (data);
`805` warns that further requests may get the user blocked, so the adapter never retries a
rate-limit error more than a few times with backoff. `RateLimiter` in `dhan.py` enforces the
per-second and per-day caps client-side.

## Error codes

Trading APIs: `DH-901` bad/expired token · `DH-902` not subscribed / no access · `DH-903`
account · `DH-904` rate limit · `DH-905` bad input · `DH-906` bad order request · `DH-907`
data fetch failed · `DH-908` server · `DH-909` network · `DH-910` other.

Data APIs: `800` internal · `804` too many instruments · `805` too many requests/connections ·
`806` data APIs not subscribed · `807` token expired · `808` auth failed · `809` token invalid ·
`810` client id invalid · `811` invalid expiry · `812` invalid date format · `813` invalid
security id · `814` invalid request.

## Exchange segments and instruments

| String (REST / feed JSON) | Feed byte | Meaning | We use it for |
|---|---|---|---|
| `IDX_I` | 0 | index values | `NSE:NIFTY`, `NSE:BANKNIFTY`, … (not tradable) |
| `NSE_EQ` | 1 | NSE cash | `NSE:RELIANCE` |
| `NSE_FNO` | 2 | NSE F&O | `NFO:NIFTY-OCT26`, `NFO:NIFTY-06OCT26-25000-CE` |
| `NSE_CURRENCY` | 3 | | ignored |
| `BSE_EQ` | 4 | | ignored |
| `MCX_COMM` | 5 | MCX | `MCX:GOLDM-OCT26` |
| `BSE_CURRENCY` | 7 | | ignored |
| `BSE_FNO` | 8 | | ignored |

`instrument` enum (historical API, from the master's `INSTRUMENT` column): `INDEX`, `EQUITY`,
`FUTIDX`, `OPTIDX`, `FUTSTK`, `OPTSTK`, `FUTCOM`, `OPTFUT` (+ currency ones we ignore).

### Instrument master

- Compact: `https://images.dhan.co/api-data/api-scrip-master.csv` (~26 MB)
- Detailed: `https://images.dhan.co/api-data/api-scrip-master-detailed.csv` (~35 MB) ← we use this
- Refreshed daily (observed `Last-Modified` ≈ 02:50 UTC). Cached once per day in
  `data/instruments/` by `dhan_instruments.py`. Update frequency is not documented.

Detailed columns: `EXCH_ID, SEGMENT, SECURITY_ID, ISIN, INSTRUMENT, UNDERLYING_SECURITY_ID,
UNDERLYING_SYMBOL, SYMBOL_NAME, DISPLAY_NAME, INSTRUMENT_TYPE, SERIES, LOT_SIZE, SM_EXPIRY_DATE,
STRIKE_PRICE, OPTION_TYPE, TICK_SIZE, EXPIRY_FLAG, BRACKET_FLAG, COVER_FLAG, ASM_GSM_FLAG,
ASM_GSM_CATEGORY, BUY_SELL_INDICATOR, BUY_CO_*, BUY_BO_*, MTF_LEVERAGE, SM_UPPER_LIMIT,
SM_LOWER_LIMIT, SM_FREEZE_QTY`.

Observed conventions (from real rows, 2026-09-18):
- NSE equities: `EXCH_ID=NSE, SEGMENT=E, INSTRUMENT=EQUITY, INSTRUMENT_TYPE=ES` (ETFs: `ETF`).
  The ticker is `UNDERLYING_SYMBOL` (`RELIANCE`, `BAJAJ-AUTO`, `M&M`); `SYMBOL_NAME` is the
  company name. `SERIES` `EQ` = normal, `BE` = trade-for-trade. `ISIN` present.
  Examples: RELIANCE=2885, TCS=11536, INFY=1594.
- NSE indices: `SEGMENT=I, INSTRUMENT=INDEX`; `SYMBOL_NAME` `NIFTY`(13), `BANKNIFTY`(25),
  `FINNIFTY`(27), `MIDCPNIFTY`(442), `NIFTY 100`(17), `INDIA VIX`(21). Spaces become `_`
  in canonical names (`NSE:NIFTY_100`).
- NSE F&O: `SEGMENT=D`, `INSTRUMENT` FUTIDX/FUTSTK/OPTIDX/OPTSTK, `INSTRUMENT_TYPE` FUT/OP.
  `SM_EXPIRY_DATE` is the exact expiry (`YYYY-MM-DD`). `EXPIRY_FLAG` `M` monthly, `W` weekly,
  also `Q`/`H`/`N`. **Weekly options share the same `SYMBOL_NAME`** (`NIFTY-Oct2026-25000-CE`
  for 06/13/19/27 Oct), so the exact date is the only unique key → weeklies get day-specific
  canonical names (`NFO:NIFTY-06OCT26-25000-CE`), monthlies get `NFO:NIFTY-OCT26-25000-CE`
  plus a day-specific alias. Lot sizes: NIFTY 65, BANKNIFTY 30, FINNIFTY 60, MIDCPNIFTY 120.
  `SM_FREEZE_QTY` (NIFTY 1756, BANKNIFTY 601) is the exchange freeze limit used for slicing.
- MCX: `EXCH_ID=MCX, SEGMENT=M`, `INSTRUMENT` FUTCOM/OPTFUT (also FUTIDX/OPTIDX for MCX
  indices). `SYMBOL_NAME` is the commodity code (`GOLDM`, `GOLD`, `SILVERM`, `CRUDEOIL`).
  **`LOT_SIZE` is always 1.0 → order quantity is in lots**, so contract value needs a
  multiplier that the master does not carry. `symbols.MCX_CONTRACT_MULTIPLIER` holds the
  MCX contract specs (GOLDM: 100 g quoted per 10 g → 10; GOLD → 100; SILVERM → 5; …).
  `TODO(dhan)`: verify the lots convention with one 1-lot paper order before live use.
- **`TICK_SIZE` is in paise** for E/D/M segments (RELIANCE `10.0` = ₹0.10, BAJAJ-AUTO
  `100.0` = ₹1, NIFTY options `5.0` = ₹0.05, GOLDM `100.0` = ₹1). Index rows say `0.05`
  (rupees). Rule used: divide by 100 when the raw value is ≥ 1.
- Rows to ignore: BSE, currency (`SEGMENT=C`), and NSE `SEGMENT=M` (NSE commodity options).

## Historical data

| Endpoint | Purpose |
|---|---|
| `POST /v2/charts/historical` | daily candles |
| `POST /v2/charts/intraday` | 1/5/15/25/60-minute candles |

Request (both): `securityId` (string), `exchangeSegment`, `instrument`, optional `oi` (bool;
adds open interest for F&O). Daily: `fromDate`/`toDate` as `YYYY-MM-DD`, **`toDate` is
exclusive**, optional `expiryCode` (0 near / 1 next / 2 far). Intraday: `interval` (1, 5, 15,
25, 60), `fromDate`/`toDate` as `YYYY-MM-DD HH:MM:SS`, **max 90 days per request**, data for the
last 5 years. Daily goes back to inception.

Response: parallel arrays `open, high, low, close, volume, timestamp, open_interest`.
`timestamp` is a plain Unix epoch (seconds). The official SDK converts it with
`datetime.fromtimestamp(ts, IST)`; the docs' examples (`1328845500` → 09:15 IST) agree. Daily
timestamps land on 00:00 IST of the session date. The ingest validator flags bars outside the
session, which would catch an offset change. `TODO(dhan)`: intraday `toDate` inclusivity is
not stated — we request an extra bar and de-duplicate.

`TODO(dhan)`: whether daily candles are adjusted for splits/bonuses is not documented. The
archive treats them as **unadjusted**; corporate actions are applied on read
(`training/ingest.py`).

## Market quote (REST)

`POST /v2/marketfeed/ltp | /ohlc | /quote` with body `{"NSE_EQ": [11536], "NSE_FNO": [49081]}`
(security ids as ints), max 1000 instruments per call, **1 request/second**. Needs
`client-id`. Response: `{"data": {"NSE_EQ": {"11536": {"last_price": 4520.0, ...}}}, "status": "success"}`.

## Live market feed (websocket, binary)

- URL: `wss://api-feed.dhan.co?version=2&token=<JWT>&clientId=<id>&authType=2`
- Limits: 5 connections per user, 5000 instruments per connection, **100 instruments per
  subscribe message** (send several). A 6th connection kills the first (disconnect code 805).
- Server pings every 10 s; the client must answer pong (the `websockets` library does this
  automatically) or the socket closes after 40 s.
- Subscribe JSON: `{"RequestCode": 15|17|21, "InstrumentCount": n, "InstrumentList":
  [{"ExchangeSegment": "NSE_EQ", "SecurityId": "1333"}, …]}`.
  Request codes: 11 connect · 12 disconnect · 15/16 ticker sub/unsub · 17/18 quote · 21/22 full
  · 23/24 full market depth (20 levels, separate product). Unsubscribe = subscribe + 1.
- Every binary message starts with an 8-byte little-endian header
  `<BHBI` = response code, message length, exchange segment byte, security id.

| Code | Packet | Layout after the header (little-endian) | Total bytes |
|---|---|---|---|
| 2 | Ticker | `f` LTP, `I` LTT epoch | 16 |
| 4 | Quote | `f` LTP, `H` LTQ, `I` LTT, `f` ATP, `I` volume, `I` total sell qty, `I` total buy qty, `f` open, `f` close, `f` high, `f` low | 50 |
| 5 | OI | `I` open interest | 12 |
| 6 | Prev close | `f` prev close, `I` prev OI | 16 |
| 7 | Market status | (no documented payload) | 8 |
| 8 | Full | quote fields, then `I` OI, `I` highest OI, `I` lowest OI, then `f` open/close/high/low, then 5 × depth `<IIHHff` (bid qty, ask qty, bid orders, ask orders, bid price, ask price) | 162 |
| 50 | Disconnect | `H` disconnect code | 10 |
| 1 | Index | `TODO(dhan)`: layout not documented; ignored | ? |
| 3 | Legacy depth | `f` LTP + 100 bytes depth (SDK) | 112 |

SDK struct strings, verbatim: ticker `<BHBIfI`, quote `<BHBIfHIfIIIffff`, OI `<BHBII`,
prev close `<BHBIfI`, full `<BHBIfHIfIIIIIIffff100s`, depth level `<IIHHff`, status `<BHBI`,
disconnect `<BHBIH`.

We subscribe in **Full** mode by default (LTP + volume + depth level 1 gives bid/ask for order
pricing); `DHAN_FEED_MODE=quote|ticker` reduces bandwidth. `LTT` is an epoch in seconds.

## Live order updates (websocket, JSON)

- URL: `wss://api-order-update.dhan.co`
- Login message: `{"LoginReq": {"MsgCode": 42, "ClientId": "<id>", "Token": "<JWT>"}, "UserType": "SELF"}`
- Messages: `{"Type": "order_alert", "Data": {...}}` with `OrderNo`, `CorrelationId`,
  `Status` (TRANSIT/PENDING/REJECTED/CANCELLED/TRADED/EXPIRED, case varies), `Quantity`,
  `TradedQty`, `RemainingQuantity`, `Price`, `TriggerPrice`, `TradedPrice`, `AvgTradedPrice`,
  `TxnType` (B/S), `OrderType` (LMT/MKT/SL/SLM), `Product` (C=CNC, I=INTRADAY, M=MARGIN,
  F=MTF, V=CO, B=BO), `Validity`, `SecurityId`, `Exchange` + `Segment` (E/D/M/C),
  `OrderDateTime`/`ExchOrderTime`/`LastUpdatedTime` (`YYYY-MM-DD HH:MM:SS`, IST),
  `ReasonDescription`, `Remarks`, `LotSize`, `Multiplier`.
- No heartbeat documented; the official SDK has no reconnect. We reconnect with backoff.

## Orders

| Op | Endpoint |
|---|---|
| place | `POST /v2/orders` |
| modify | `PUT /v2/orders/{order-id}` |
| cancel | `DELETE /v2/orders/{order-id}` |
| slice (freeze-limit helper) | `POST /v2/orders/slicing` |
| get by id | `GET /v2/orders/{order-id}` |
| get by our tag | `GET /v2/orders/external/{correlation-id}` |
| order book | `GET /v2/orders` |
| trade book | `GET /v2/trades` |
| trades of an order | `GET /v2/trades/{order-id}` |

Place body: `dhanClientId, correlationId, transactionType (BUY/SELL), exchangeSegment,
productType (CNC/INTRADAY/MARGIN/MTF/CO/BO), orderType (LIMIT/MARKET/STOP_LOSS/
STOP_LOSS_MARKET), validity (DAY/IOC), securityId, quantity, disclosedQuantity, price,
triggerPrice, afterMarketOrder, amoTime, boProfitValue, boStopLossValue`.
Response: `{"orderId": "...", "orderStatus": "TRANSIT"}`.

- **`correlationId` is max 30 chars, `[A-Za-z0-9 _-]`** → our idempotency tag
  (`core.types.new_tag()`) is 27 chars. Manual orders from the app have an empty
  `correlationId`; the adapter names them `dhan:<orderId>`.
- Modify body: `dhanClientId, orderId, orderType, legName (BO/CO only), quantity, price,
  disclosedQuantity, triggerPrice, validity`. `quantity` must be the placed quantity (v2 note),
  so the adapter re-reads the order and fills unchanged fields.
- Product mapping: `MIS→INTRADAY`, `CNC→CNC`, `NRML→MARGIN`.
- Status mapping: `TRANSIT→PENDING`, `PENDING→OPEN`, `PART_TRADED→PARTIAL`, `TRADED→FILLED`,
  `CANCELLED→CANCELLED`, `REJECTED→REJECTED`, `EXPIRED→CANCELLED`, `TRIGGERED→OPEN`,
  `CLOSED→FILLED` (super orders).
- Order-book rows carry `orderId, correlationId, orderStatus, transactionType, exchangeSegment,
  productType, orderType, validity, tradingSymbol, securityId, quantity, disclosedQuantity,
  price, triggerPrice, afterMarketOrder, boProfitValue, boStopLossValue, legName, createTime,
  updateTime, exchangeTime, drvExpiryDate, drvOptionType, drvStrikePrice, omsErrorCode,
  omsErrorDescription, algoId, remainingQuantity, averageTradedPrice, filledQty`.
- Trade rows: `orderId, exchangeOrderId, exchangeTradeId, transactionType, exchangeSegment,
  productType, orderType, tradingSymbol, securityId, tradedQuantity, tradedPrice, createTime,
  updateTime, exchangeTime, drv*`.
